Client Setup and Project Discovery

Run commands from the docs-system repository unless a step names another directory. This installation references the development checkout through absolute paths. Keep Bun and the checkout available to each client.

Install the Connection

1. Install workspace dependencies from the parent Core directory. Its workspace lockfile owns the linked package dependencies.

cd ..
bun install
cd docs-system

2. Preview the installation. Use --clients codex,claude,pi to select clients, or omit the flag for all three. Preview does not change client files.

bun packages/docs-mcp/src/cli.ts install

3. Write the installation and save its report. Changed files receive backups. The saved report is the input to the guarded restore command.

bun packages/docs-mcp/src/cli.ts install --write > /tmp/codecaine-docs-install.json
bun packages/docs-mcp/src/cli.ts doctor

4. Restart Codex and Claude Code. In pi, run /reload. Open a new task in the target workspace so the client can load the installed skill and tools.

Discover the Workspace

A single connection routes operations to explicit project IDs. Start in a project to work on its docs, or in Core to discover multiple declared projects. Discovery uses the workspace itself, members.json directory entries, supported package workspace patterns, and explicit projects in codecaine.docs.json. It does not scan the whole machine.

bun packages/docs-mcp/src/cli.ts discover --workspace ..

The workspace defaults to --workspace, then CLAUDE_PROJECT_DIR, then the process working directory. MCP roots can update the client workspace. pi passes its session directory. If discovery is wrong, explicitly supply the intended absolute workspace to docs_discover and begin a new task there.

Use this optional configuration in a project or umbrella workspace. Omit projects for a single repository. The docsRoot directory must contain at least one valid normalized doc.json bundle.

{
  "name": "my-workspace",
  "docsRoot": "docs",
  "products": ["docs"],
  "projects": ["child-project-a", "child-project-b"]
}

Member paths must remain inside the workspace. docsRoot must remain inside its project, including after resolving symlinks. Absolute member paths and recursive ** globs are unsupported. Declare explicit relative members instead. Markdown-only repositories are not migrated; malformed candidate bundles produce discovery warnings.

Project IDs depend on the project name and canonical docs-root path. Rediscover after moving or renaming a checkout. For a prompt that edits two projects, use the two returned IDs on separate tool calls and check each changed page. There is no cross-project transaction or rollback.

Inspect Changes in the Shared UI

bun packages/docs-mcp/src/cli.ts ui --workspace .. --project docs-system --port 4808

This workbench uses the same editing service as the external clients. Valid tool edits become visible immediately. Existing standalone or kernel workbenches have separate process-local coordination; finish their edits before editing the same documents through MCP.

Website publication remains a separate build, export, or embedding integration over the corpus. Editing a document does not deploy it. The local MCP service is not the public website server.

Skills and Component Knowledge

Change the maintained source, regenerate derived references, and refresh installed copies. Editing an installed skill alone creates a local difference that the next installation can overwrite.

Docs MCP describes the service and the shared authoring context.

Maintained Sources

packages/docs-mcp/skills/codecaine-docs/SKILL.md owns the external-agent workflow, trigger description, and skill metadata.

packages/docs-model/src/authoring-guidance.ts owns AUTHORING_BUNDLES, the standard and style document lists, component catalog assembly, and shared rendering.

packages/docs-model/src/components/index.ts registers component bundles. Each component manifest supplies authoring metadata with whenToUse, example, and docsPath.

packages/docs-model/src/visual-component-guidance.ts owns the shared visual-selection text used with the component catalog.

packages/docs-mcp/src/guidance.ts loads and validates canonical documents, hashes guidance sources, and generates portable skill references.

What the Agent Receives

The server advertises tools and startup instructions. docs_begin returns the writing standards, full component-selection catalog, task ID, and snapshot identity. docs_guidance can retrieve one component reference by component name. The MCP resource codecaine://docs/guidance exposes current rendered guidance. There is no MCP prompts capability in this implementation.

The installed skill tells the coding agent when and how to use those tools. Installation places references/standards.md, references/components.md, references/components/<name>.md, and snapshot.json beside SKILL.md. These files are generated from the canonical corpus and manifests; they are not independent standards.

The catalog covers rich text, annotated Code, File Tree, Structured Table, State Shape, Interaction Surface, Canvas, Sequence, and Process Outline. Component purposes load together; detailed references can be fetched only when needed. Connecting an MCP does not prove a client selected the skill. Test implicit use in each client.

Change Writing or Component Guidance

1. For wording and standards, read the canonical document through Docs tools, apply a typed edit, and run docs_check. For tool-use workflow, edit the source SKILL.md. Project-specific standards overrides are not implemented.

2. For component selection, update the component manifest authoring metadata and its canonical reference together. Change the shared visual guidance only when the selection rule itself changes.

3. For a new component, register its bundle, state schema, typed actions, and rendering using the existing component contract. Add its canonical documentation and manifest metadata. A skill reference alone does not implement editing tools.

4. Refresh the client installation and begin a new authoring task. Restart the service first when imported TypeScript changed. Inspect docs_guidance for the changed component and verify a real typed edit.

Built-in Agents and PromptKit

The Docs Lab context loader at packages/docs-kernel/catalog/docs-lab-editor/context/index.ts and the sibling agent-kernel/catalog/docs-writer/context/index.ts both use the shared authoring-guidance renderer. Their prompts, model configuration, context loading, and staged editing sessions remain owned by those agents. External MCP edits do not run those agents.

PromptKit remains responsible for its own prompt machinery. This integration has no PromptKit editing adapter and does not turn every internal prompt into an MCP prompt. A future product service can follow the same separation between typed operations, maintained knowledge, and client installation. Such adapters must document their own state ownership and validation before claiming coverage.

Reload Runtime Code

1. End active documentation tasks after checking their changed pages. Finish any standalone or kernel editing activity on the same documents.

bun packages/docs-mcp/src/cli.ts status
bun packages/docs-mcp/src/cli.ts stop
bun packages/docs-mcp/src/cli.ts start

2. Reconnect coding clients and restart shared workbenches. Workbenches bind to the service URL and token at launch. Begin a new task and read fresh hashes before continuing.

3. Run the affected validation checks and record a snapshot after the code and guidance settle.

bun test packages/docs-mcp/src
bunx tsc -p packages/docs-mcp/tsconfig.json --noEmit
bun packages/docs-mcp/src/cli.ts snapshot --out /tmp/codecaine-docs-snapshot.json

What a Snapshot Records

The development manifest records runtime package source hashes, repository commits and dirty flags, guidance sources and identity, client declarations, and the tool-contract hash. Source hashing covers package.json and selected src TypeScript and JSON files, excluding tests and fixtures. A snapshot identifies these inputs; it is not a full repository archive.

Runtime coverage includes docs-mcp, docs-model, docs-server, docs-index, docs-workbench, Canvas, Sequence, and Annotations. Repository metadata includes docs-system, canvas, sequence, annotations, agent-kernel, and prompt-kit. A recorded repository is not proof that it has a product adapter or normalized documentation corpus.

The package is currently private and uses workspace dependencies. The skill has version metadata, while snapshot hashes identify the actual development sources. No release lockfile installer, published compatibility matrix, or automatic six-package version selection exists. Changing a version field alone does not update installed files or running services.

Validation and Recovery

Start with doctor for installed-file differences, discovery for workspace coverage, and a small real edit for end-to-end acceptance. These checks answer different questions.

Repeatable Acceptance

1. Open a new client session in the target project. Ask it to explain one existing documentation page without editing. Expect docs_discover and a tree, search, or read call against the correct project ID.

2. Ask for one source-supported documentation correction without naming the tools. Expect docs_begin before mutation, docs_read for the current document hash, and a typed edit with the returned task_id and expected_hash. docs_guidance is useful for a component-specific reference but is not required on every edit.

3. Expect docs_check on each changed page and docs_end when the task finishes. Read back the page and inspect it in the shared UI. A successful tool response alone does not establish that the prose is correct.

4. For a Canvas or Sequence edit, expect docs_component_read and an advertised typed component action using the document and sidecar revision hashes. For a multi-project request, verify each project separately and report partial success explicitly.

5. Repeat the implicit request in each supported coding client. Separately exercise a built-in agent through its existing staged review flow after shared guidance changes. Protocol tests, installer checks, and external edits do not prove model behavior in every client.

Find Tool Names

bun packages/docs-mcp/src/cli.ts tools
bun packages/docs-mcp/src/cli.ts doctor
bun packages/docs-mcp/src/cli.ts discover --workspace ..

Use advertised schemas for exact arguments. Common edits include docs_write_text, docs_insert, and docs_apply_ops. Component action names are generated from the registered actions; do not infer a name or bypass an unsupported action with a filesystem write.

Backups and Restore

bun packages/docs-mcp/src/cli.ts restore /tmp/codecaine-docs-install.json
bun packages/docs-mcp/src/cli.ts restore /tmp/codecaine-docs-install.json --write

Preview restore first. Restore verifies backup and installed-file hashes and refuses to overwrite post-install changes. Claude can update its configuration during normal use, so an exact restore may refuse. To remove only its MCP entry, use claude mcp remove codecaine-docs -s user and preserve the newer file. Skill copies and pi configuration require their own reviewed cleanup.

Local State and Evidence

Runtime state defaults to ~/.local/state/codecaine-docs or CODECAINE_DOCS_STATE_DIR. daemon.json contains the bearer credential and service address. daemon.lock and startup.lock coordinate startup; service.log records daemon output. Do not share daemon.json as a diagnostic artifact. No model API key is needed for this editing service.

Task contexts and guarded undo are process-local. docs_end releases guidance and does not revert applied edits. Stopping the service loses that in-memory state, while saved documents remain on disk. Cross-project edits are not atomic.

Save tool results, final hashes, lint findings, and a reviewed content diff when recording acceptance. Label a user-reported successful exercise separately from automated evidence. Keep those dated records in objectives/docs-mcp-integration/artifacts and the handoff, outside the maintained corpus.

Page Creation, Move, Rename, and Deletion

Page and section operations now include descendants. docsmove and docsrename preview their complete file and reference changes; apply with preview:false and expectedtreehash. Use docssettitle for display titles.

Management operations keep recovery journals and expose docsmanagementrestore. Restore refuses subsequent edits or added descendants. Shared-store operations serialize during a reorganization; independent service processes remain separate authorities.

To delete, first call docs_delete with path and expected_hash. Its default preview returns the files to remove and tree_hash. Review those files and the user's deletion authorization. Apply with preview:false and expected_tree_hash set to that preview hash. Changes to corpus files invalidate the preview. No user documentation is deleted merely by requesting the preview.

Deletion refuses external references into the deleted subtree. Relocate shared assets with docsassetmove before removing their owner page. Section moves rewrite both descendant links and shared or external asset paths. Use recursive:true to request deletion of a section and all descendants.

After a move or rename, read the destination, inspect rewritten links, and run docs_check on affected pages. After deletion, inspect docs_tree and check remaining affected pages. Reconnect clients after the service restart so their tool catalogs include docs_move, docs_rename, and docs_delete. Restart shared workbenches when the daemon address changes.

Rename or Move a Section

1. Discover the project, begin a task, and read the section root with docs_read. Keep its hash. docs_rename takes the section path and a new directory name; docs_move takes the source path and a destination path in the same project.

2. Call the operation with its source expected_hash. Preview is the default. Review files, children, and rewritten_sources. The service plans descendant document links, Canvas links, media references, and paths to assets outside the moving subtree.

3. Apply with preview:false and expected_tree_hash set to the preview tree_hash. A change anywhere in the captured corpus invalidates that plan. Read the destination and run docs_check on affected documents. A directory rename preserves page IDs, block IDs, and titles; use docs_set_title when the display title should change.

Move a Shared Canvas Before Deleting Its Old Page

1. Use docs_assets or the referencing block to locate the Canvas. Read its source path with docs_asset_read to get the asset hash. Asset paths are relative to the docs root.

2. Preview docs_asset_move with path, to, and expected_hash. The destination must be in an existing page assets directory and retain the component file type. For example, move an Architecture Canvas into System Design assets/canvases before removing Architecture.

3. Apply the reviewed preview. The service moves the asset bytes and rewrites referring src values. It also maintains attachment links, media posters, and annotation Canvas targets. Read the System Design page and component, then run docs_check to verify the surviving embed.

4. Preview docs_delete on the old page with its fresh document hash. Repair any remaining inbound links. Use recursive:true only when the intended deletion includes all children. Apply the reviewed preview and inspect the remaining tree.

A reference to a file inside an old page does not transfer ownership. Move the asset itself before deleting the owning page. Deletion refuses references from outside the deletion set, including references to descendant pages and bundled assets.

Recovery and Coordination

Keep tree_change_id from every applied management operation. docs_management_restore previews restoring that change. Apply its reviewed tree hash to restore captured content. Restore refuses changed files, added descendants, occupied original paths, and active draft locks. It does not overwrite later work.

Management journals live under .changesets/file-management/<id>. They record the plan, captured bytes, application status, and hashes after application. Deleted bundles remain in the journal for recovery. Journals are not published documentation. A process or storage failure may require inspecting the retained journal; a failed rollback is reported explicitly.

Shared-store callers serialize corpus operations, while document and sidecar locks coordinate lower-level edits. Management checks the complete corpus before applying and checks draft locks on affected files. Separate service processes still do not share in-memory coordination. Finish standalone or internal editing activity before reorganizing the same corpus.

Symlinks, overlapping source/destination paths, destination collisions, invalid rewritten documents, and ambiguous asset paths are rejected. Management restore is distinct from docs_undo, which handles tracked content patches. Cross-project relocation is not an operation; use each project's explicit tools and ownership.

Docs MCP

The Docs MCP package connects external coding agents to the existing Docs service. Codex and Claude Code use an MCP stdio connection. pi Agent uses an extension that forwards the same tool definitions.

Read and Edit

Discover the active workspace with docs_discover. Before editing, call docs_begin to load shared writing standards and component guidance. Read the target document through docs_read, then supply its revision hash and the task ID to a typed editing tool. Valid changes apply immediately.

The service rejects invalid structure and stale revisions. Editing calls return draft writing findings. Run docs_check before reporting completion, and repair required findings or state what remains unresolved. A failed update in one project does not roll back successful updates in another project.

Component Knowledge

Component manifests declare selection guidance and examples. The shared authoring-guidance renderer supplies the catalog to external tools and both built-in Docs agent contexts. Use docs_guidance with a component name to read its canonical reference.

Shared Service

The CLI automatically starts one local editing service. The client connections share that process, and explicit project IDs route operations to a discovered corpus. The shared workbench mode proxies its API to the same authority. Standalone workbench and kernel modes remain available with their existing process-local state.

Development Setup

From the Docs System repository, run bun packages/docs-mcp/src/cli.ts install to preview the client configuration and skill files. Add --write to install with backups. Run doctor to check those installed files. Restart the coding clients or reload pi after installation.

Use the ui command with a workspace and project ID to inspect edits through the shared workbench. Publication remains separate: the same corpus can be exported or embedded in a website without deploying after every edit.

Compatibility

The snapshot command records package source hashes, repository revisions, tool contracts, and guidance sources. Standards reload between documentation tasks. Imported implementation changes require restarting the service. The built-in Docs Lab editor and generic docs-writer retain their existing staged review behavior.

Content and component edits expose guarded undo while the service is running. Page creation does not expose undo because the existing tree inverse cannot safely remove a page after later additions.

Maintained Procedures

Docs MCP Maintenance contains the setup, skill-authoring, synchronization, and recovery procedures.

Process and Task Ownership

Codex and Claude use stdio MCP bridges; pi uses its extension bridge. They connect to one authenticated loopback daemon per state directory. The service resolves an explicit project to its canonical docs root and calls the existing store through typed tools. No model or kernel process is started by an external documentation task.

The service owns workspace membership and in-memory task snapshots. Store operations own structural validation, revision checks, and root-scoped mutation coordination. Task IDs are bound to the workspace; they pin authoring knowledge without creating a transaction. Direct valid edits persist immediately. The shared workbench proxies to this same daemon. Standalone workbenches and kernel processes retain independent process-local state.

Ecosystem Coverage

The implemented adapter edits Docs corpora, including documentation for other packages when those corpora are discoverable. Embedded Canvas and Sequence operations use the Docs component adapters. This does not provide standalone Canvas, Sequence, PromptKit, Annotations, or Agent Kernel product services. Recording sibling repositories in a development snapshot does not establish adapter support.

Canonical corpus standards, style documents, component references, manifests, and the source skill feed generated knowledge. Installed skill references are copies. Internal context loaders share the renderer while retaining their own prompts and staged editing lifecycle. Runtime source fingerprints guard against using changed implementation files in an existing service. Published release compatibility and automatic package-version resolution remain unimplemented.
