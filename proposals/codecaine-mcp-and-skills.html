1. Agreed Direction

Make documentation easy to edit from Codex, Claude Code, and pi Agent without explaining the Docs implementation each time.

One user-level installation provides the Codecaine MCP connection and companion skills. A lightweight local service starts automatically and coordinates access to documentation across projects. The external coding agent performs the work directly through the tools. No internal specialist run, background model, or kernel runtime is required.

The intended experience
Open the GameCube Decomp harness and ask for an existing page to be updated. The agent discovers the corpus, reads the relevant standards, chooses suitable components, edits through the connected tools, and checks the result in the existing documentation system.

Documentation remains the source for authoring knowledge. Skills explain the workflow, component guidance explains what to use and why, and typed tools constrain how content is read and written.

The user confirmed this initial scope after the design interview. This document records that agreement. It does not authorize implementation, installation, or edits to project documentation.

Selectable Products, Automatic Dependencies

Core currently contains Docs System, Agent Kernel, Prompt Kit, Canvas, Sequence, Annotations, and Observatory. The workspace and test configuration cover six ecosystems, excluding Observatory. This inventory does not require six skills, six servers, or six simultaneous releases. Resolve the dependencies needed by the selected products.

Website Publication

The same documentation source can be exported for hosting or embedded in a website. Publication can run through a repository hook or a separate website build. Editing does not deploy automatically. Remote authoring and deployment automation are outside this initial scope.

3. Skills and Components

The agent should know that components exist and when to use them, before it needs to learn their editing details.

Navigation and Authoring Skill

Discover the active project, read its documentation through the tools, load the shared writing standards, perform typed edits, and check completion.

Complete Component Catalog

Expose each registered component's purpose and selection criteria. Include custom components so the user does not need to mention their existence.

Focused Component References

Load detailed instructions and examples for selected components. Give complex workflows dedicated skills where useful; simple components can use reference files.

Typed Editing Tools

Generate supported operation schemas from the component definitions. These explain how to edit; selection guidance explains why to choose a component.

For example, guidance should distinguish State Shape, Interaction Surface, and Sequence by the question each answers. Register purpose, selection criteria, and examples alongside component metadata, using canonical documentation references for fuller explanations.

Registration must reach the client.
MCP tool discovery does not automatically install skills or load every resource. The installer supplies the supported skill bindings for Codex, Claude Code, and pi Agent. The editing workflow retrieves applicable standards and component guidance through the same maintained sources.

The Agent Skills format supports SKILL.md with supporting references; it does not define a special subskill relationship. Keep the initial catalog compact and load detailed material as needed. Optional MCP prompts can provide explicit workflow starters, but automatic authoring behavior must not depend on selecting one.

Use existing shared standards. Project-specific standards and overrides are deferred. The existing internal agents can reuse the same guidance sources without becoming part of the external editing execution path.

4. Synchronized Versions

Install compatible tools, skills, and standards together. Begin with local development snapshots.

The first implementation does not need published versions of every Core package. Record exact source revisions and content hashes, including dirty local content, so the installed combination can be identified.

Snapshot RecordPurpose
Selected products and dependenciesIdentify the resolved package sources needed for the enabled workflows.
MCP adapter and tool contractsIdentify the operations and schemas exposed to the client.
Skills and generated referencesRecord content hashes and the canonical source mappings.
Standards and component guidanceIdentify the exact rules and selection guidance loaded for authoring.
Client compatibilityRecord the client bindings and tested capabilities for Codex, Claude Code, and pi Agent.

Maintain Each Rule Once

  1. Keep canonical sources with their owner. Docs owns shared writing standards; components own selection metadata and supported operations.
  2. Generate the consuming views. Render references for skills and MCP resources from the same sources. Reuse that guidance in the existing internal context loaders.
  3. Check the combination. Validate skill format, references, generated output, and tool contracts. Test authoring behavior separately from structural correctness.
  4. Refresh between documentation tasks. Keep tools and guidance consistent within a task, record its snapshot, and report incompatible changes rather than switching silently during an edit.
Skill metadata is not dependency enforcement.
The Agent Skills specification permits version metadata and compatibility notes, but defines no dependency resolver or lockfile. Codecaine owns the snapshot and later release-lock convention.

When distribution requires releases, publish tested combinations and update or roll back the adapter and companion skills together. Packages can keep independent version numbers. Users should not manually assemble matching versions.

Live target documents still use content-revision checks. The standards snapshot used to author them is a separate identity. Changing a standard regenerates its affected views; changing a tool contract also requires checking the skills that reference it.

Calls identify the project and target document explicitly. One prompt can operate on multiple projects without switching MCP connections. Read tools return useful rendered content and stable identifiers; write tools preserve the model's structure through supported operations.

Immediate Edits with Validation

  1. Reject malformed structure before writing. Keep schema validation and content-revision checks in the owning service.
  2. Apply valid edits immediately. Temporary writing-rule findings may remain during multi-step edits and must be returned to the agent.
  3. Check before reporting completion. The agent repairs required findings or states what remains unresolved. Valid intermediate edits remain visible.
  4. Report partial multi-project results. If one project update fails, retain successful edits and identify the unfinished work. Cross-project transactions are deferred.

MCP exposes the constrained interface; it does not itself remove an external agent's filesystem access. Installed guidance routes documentation work through the tools. Service-side checks enforce correctness for calls made through that interface.

Why Share the Service?

Current mutexes, draft locks, undo state, and events are process-local. Independent client processes writing directly would not share that coordination. Client adapters should reach a shared authority, including for UI edits. Multi-project isolation must scope locks by corpus root as well as relative document path.

A documentation task here means an editing activity in the external agent. It does not require a background task queue, an internal agent session, or the MCP Tasks extension.

6. Setup and Discovery

  1. Install once at user level. Configure the MCP connection and companion skills for Codex, Claude Code, and pi Agent together. Do not copy the integration into every repository.
  2. Connect from the active workspace. Automatically start or reuse the lightweight editing service. No separate MCP connection is needed for each project.
  3. Discover conventional documentation. Recognize a valid docs/ corpus. At a workspace root, inspect declared member projects. Use a small project configuration for exceptions such as another docs path or enabled extensions.
  4. Choose targets through the tools. Default to the current project. Include other discovered projects when the request names them or asks for workspace-wide changes.

Discovery stays within the active workspace. It does not require a machine-wide registry or unrestricted recursive filesystem scan. Reuse existing workspace membership where possible; Core's member list identifies repositories but does not currently declare their docs roots.

Client adapters must supply the active workspace reliably. Exact configuration syntax, startup mechanics, and transport mappings remain implementation choices to verify against all three supported clients.

A Docs-only selection enables documentation workflows and their required dependencies. Other products become available through the same installation as their interaction-service adapters are added.

7. Acceptance

The first success is easy, real editing in the existing documentation system through connected tools.

  1. Connect all three clients. Install the integration for Codex, Claude Code, and pi Agent. Confirm tools and skills are discoverable without inspecting the Docs repository manually.
  2. Edit a GameCube harness page. Use an ordinary documentation request without naming tools, standards, or components. The agent discovers the corpus, loads guidance, selects suitable components, makes valid edits, and checks the result.
  3. Verify the existing system sees the changes. Read back through the service and inspect the result in the normal documentation UI. Confirm invalid structure is rejected and writing findings are visible.
  4. Update two projects in one request. Verify routing and isolation. Confirm successful changes remain when another project update fails.
  5. Change one standard between tasks. Regenerate affected guidance and identify the new snapshot. Verify the next task receives it while the previous task's recorded identity remains intact.

After this works, apply the same pattern to other existing interaction services. Package layout and exact tool mapping should follow the simplest viable adapter rather than introduce a new orchestration framework.

Acceptance is not yet verified.
Source inspection established reusable building blocks. No integration has been implemented or installed, and no project documentation has been edited as part of this design work.

8. Decision Tree

The initial decision frontier is settled. The branches below record the agreed constraints and the implementation work that follows from them.

External Agent Does the Editing

Direct tools → immediate valid writes → structural validation → final writing check.

Deferred: specialist delegation and mandatory staged review.

One Integration, Multiple Projects

User-level installation → workspace discovery → explicit project targets → independent update outcomes.

Deferred: machine-wide registry and cross-project transactions.

Knowledge Arrives Automatically

Client skill bindings → shared standards → complete component catalog → focused references and typed operations.

Deferred: project-specific standards and overrides.

Docs Establishes the Pattern

Existing service coverage → GameCube acceptance → three-client verification → other interaction services.

Deferred: standalone product adapters and published package releases.

Implementation Details to Resolve

Package placement, client-specific bindings, configuration schema, transport selection, startup lifecycle, snapshot boundaries, and exact tool mappings remain engineering work within these agreed constraints. Inspect and test them before claiming support. They do not reopen the initial product scope.

Website publication remains a downstream use of the same source, through a repository hook, build, or embedding workflow. No deployment-on-edit behavior is planned.
